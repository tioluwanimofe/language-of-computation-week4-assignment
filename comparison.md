# Comparison of my books.db with my partner's

**The two databases do not hold the same data.** They hold the same books, and every one of the 23 CSV columns matches, but the `changes_repairs` note differs on 892 books.

| | My books.db | Partner's books.db (Melissa Forte) |
|---|---:|---:|
| Books | 10014 | 10014 |
| Books only in this database | 0 | 0 |
| Books in both with a different value | 892 | 892 |

## How the comparison was made

- Two rows are the same book when they have the same `book_id` (rules.md, rule 8). Neither database has a row without a `book_id`.
- Both databases have one table, `books`, with the same 24 columns: the 23 CSV columns plus `changes_repairs`. Every column was compared. Neither database has a column that only records when a row was loaded, so none was left out.
- Both databases are the result of the same three runs: books.csv, books.csv again, books-batch2.csv.

## Why our data differs

All 892 differences come from one rule: answer 8 in rules.md, and the follow-up to it about example 8.

Answer 8 says the label "wrong number of digits (N)" counts digits only. The follow-up then says to add that label only when the value *also* has the wrong number of characters. An isbn13 value like `9.7806182603e+12` has 13 digits (11 before the `e`, plus the `12` after it) but 16 characters. So the question is whether the label needs both things to be wrong, or just the characters.

- My partner's code reads it as both: the digit count has to be wrong *and* the length has to be wrong. 13 digits is the right number for an ISBN-13, so there is no digit-count label.
- My code reads it as the characters only: the value isn't 13 characters long, so it adds the label with the number of digits it has, which gives the odd-looking "wrong number of digits (13)".

My partner's reading is the right one. A label that says "wrong number of digits (13)" on an ISBN-13 contradicts itself, and the word "also" in the follow-up means the digit count must be wrong too.

What let it through:
- **The rule** could be read two ways, because it never says plainly that the digit count itself must be wrong.
- **The tests** didn't catch it. None of the 15 examples in the table has a scientific-notation value with exactly 13 digits. Examples 11 and 12 both have 14 digits, where both readings give the same answer.
- **The code** followed the wrong reading, and nothing stopped it.

To fix it, the rule should say "add the digit-count label only when both the number of digits and the number of characters are wrong", the examples table should get an example like `9.7806182603e+12`, and my code should be changed to match. Then both databases would be the same.
